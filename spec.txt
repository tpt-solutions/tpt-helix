1. Purpose
TPT Helix is a next-generation web platform built from first principles. It is not a browser — it is the successor to the browser.
The modern web has become an accidental operating system: bloated, insecure, and economically captured by surveillance capitalism. Thirty years of backward compatibility have turned the web platform into an archaeological dig of accumulated complexity. JavaScript, designed in 10 days for form validation, now underpins the global economy. The browser has become a universal runtime that nobody designed and nobody can replace.
TPT Helix replaces this. It is:
A WASM-native application platform that renders web content without a JavaScript engine
An AI-accelerated migration system that ports existing web applications to native WASM
A capability-secure runtime where applications declare what they need, not what they can take
A memory-efficient engine that uses 60–80% less RAM than Chromium for equivalent workloads
TPT Helix does not compete with Chrome. It obsoletes the architecture that made Chrome necessary.
2. Goals
2.1 Primary Goals
| #  | Goal                               | Success Criteria                                                                                 |
| -- | ---------------------------------- | ------------------------------------------------------------------------------------------------ |
| G1 | **WASM-Native Runtime**            | Execute web applications compiled to WASM without a JavaScript interpreter in the hot path       |
| G2 | **AI-Accelerated Migration**       | Port 80% of common web application patterns from JS to Rust/WASM autonomously within 12 months   |
| G3 | **Capability Security**            | Replace origin-based security with capability-based access control; no ambient authority         |
| G4 | **Memory Efficiency**              | Achieve ≤150 MB base RAM for a single complex application (e.g., video player, document editor)  |
| G5 | **Content-Addressed Distribution** | Replace location-based URLs with content-addressed identifiers (IPFS-style) for immutable assets |

| #   | Goal                     | Success Criteria                                                                                                 |
| --- | ------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| G6  | **Legacy Compatibility** | Run existing JavaScript applications via embedded lightweight interpreter (QuickJS/Boa) during transition period |
| G7  | **Cross-Platform**       | Native builds for Linux, macOS, Windows, Android, iOS, and embedded (Raspberry Pi, ESP32-class where feasible)   |
| G8  | **Developer Experience** | Provide source-language choice: TypeScript-subset, Rust, or Zig → compile to WASM with WIT interfaces            |

2.3 Non-Goals
| #   | Non-Goal                                                    | Rationale                                                                                                                            |
| --- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| NG1 | **Pixel-perfect Chrome compatibility**                      | The web platform spec is 50M+ lines of accumulated complexity. Helix targets a clean subset + migration path, not bug-for-bug parity |

| NG3 | **Surveillance-based monetization**                         | No telemetry, no fingerprinting, no ad-tech integration. Revenue from licensing, support, and enterprise deployment                  |
| NG4 | **Immediate consumer market dominance**                     | Target enterprise, embedded, and controlled-content ecosystems first. Network effects follow utility                                 |

5. Capability Model
5.1 Principles
No ambient authority. A module has no access to anything not explicitly granted.
User grants, not site requests. The user decides what an application receives, not the application.
Fine-grained, revocable. Capabilities are per-resource and can be revoked at any time.
Composable. Capabilities can be delegated between modules.
5.2 Capability Types (WIT Interfaces)
The canonical WIT is `crates/tpt-helix-wit/wit/helix.wit`, package `helix:runtime@0.1.0`.
The block below is a verbatim copy. `crates/tpt-helix-wit/tests/spec_sync.rs` fails if the
two diverge, so change `helix.wit` and this block together.

Interfaces: `network` (fetch), `storage` (get/set/delete), `dom` (create-element, set-text,
set-attribute, append-child, on-click, on-event), `media` (create-player, play, pause, seek).
Worlds: `helix-host` exports all four interfaces, so the host implements them. `helix-guest`
imports them and exports `run` and `dispatch(handler-id)`. The host calls `dispatch` for each
handler an event triggers. Errors are plain `string`s. Callbacks cross the boundary as opaque
`handler-id`s, not function values.

[BEGIN helix.wit]
// Helix Runtime WIT interfaces.
//
// These are the canonical capability interfaces a guest WASM module consumes
// from the Helix Runtime host. They are the source of truth for the generated
// host (`Guest` trait) and guest (call shim) bindings produced by
// `wit_bindgen`.
//
// Package `helix:runtime@0.1.0` generates Rust modules under
// `helix::runtime::{network, storage, dom}`.

package helix:runtime@0.1.0;

// ---------------------------------------------------------------------------
// network
// ---------------------------------------------------------------------------

interface network {
    record request {
        method: string,
        url: string,
        headers: list<tuple<string, string>>,
        body: option<list<u8>>,
    }

    record response {
        status: u16,
        headers: list<tuple<string, string>>,
        body: list<u8>,
    }

    // Issues a request and resolves to the response, or an error string
    // describing why the (capability-scoped) request was rejected / failed.
    fetch: func(req: request) -> result<response, string>;
}

// ---------------------------------------------------------------------------
// storage
// ---------------------------------------------------------------------------

interface storage {
    get: func(key: string) -> option<list<u8>>;
    set: func(key: string, value: list<u8>) -> result<_, string>;
    delete: func(key: string) -> result<_, string>;
}

// ---------------------------------------------------------------------------
// dom
// ---------------------------------------------------------------------------

interface dom {
    record element-id {
        id: u64,
    }

    create-element: func(tag: string) -> element-id;
    set-text: func(el: element-id, text: string);
    set-attribute: func(el: element-id, name: string, value: string);
    append-child: func(parent: element-id, child: element-id);

    // Registers a previously-declared click handler (identified by an opaque
    // `handler-id`) against an element. The runtime invokes the handler when
    // the element is activated. Callbacks cross the component boundary as
    // handles/ids rather than first-class function values.
    on-click: func(el: element-id, handler-id: u64);

    // Registers a handler for a named DOM event such as `submit`, `change`,
    // `input`, `play`, `pause`, or `ended`. The event name is lowercase ASCII
    // letters, up to 32 bytes. Like `on-click`, the callback is an opaque id.
    on-event: func(el: element-id, event: string, handler-id: u64);
}

// ---------------------------------------------------------------------------
// media
// ---------------------------------------------------------------------------

interface media {
    record player-handle {
        handle: u64,
    }

    record video-config {
        codec: string,  // "h264", "vp9", "av1"
        width: u32,
        height: u32,
        bitrate: u32,
    }

    // Creates a media player for the given configuration. Fails with an error
    // string when the module lacks a `media` capability covering the requested
    // resolution, or the configuration cannot be satisfied.
    create-player: func(config: video-config) -> result<player-handle, string>;
    play: func(handle: player-handle);
    pause: func(handle: player-handle);
    seek: func(handle: player-handle, time-ms: u64);
}

// ---------------------------------------------------------------------------
// worlds
// ---------------------------------------------------------------------------

// The host (Helix Runtime) *exports* these capability interfaces: a guest
// component imports them and calls them. `wit_bindgen` generates a `Guest`
// trait per interface (under `host::exports`) that the native host implements.
// Named `helix-host` to match the `world:` selector in `crates/tpt-helix-wit`.
world helix-host {
    export network;
    export storage;
    export dom;
    export media;
}

// A guest module *imports* the same interfaces. `wit_bindgen` generates the
// call shims (`helix::runtime::network::fetch`, etc.) a guest compiles against.
// It also *exports* a `run` entry point that the host invokes after
// instantiation to drive the module (see the smoke-test guest in
// `crates/tpt-helix-guest-example` and the wasmtime host in `crates/tpt-helix-runtime`).
// Named `helix-guest` (not `helix`) to avoid colliding with the `helix`
// package namespace in wasmtime's codegen.
world helix-guest {
    import network;
    import storage;
    import dom;
    import media;
    export run: func();
    // Called by the host once per handler that a DOM event triggers. The argument
    // is the handler id the guest registered with `on-click` or `on-event`.
    export dispatch: func(handler-id: u64);
}
[END helix.wit]

5.3 Grant Flow
User opens application
    │
    ▼
Application declares required capabilities:
    "I need network:fetch to api.example.com"
    "I need storage:local (10MB)"
    "I need dom:full"
    "I need media:video (720p max)"
    │
    ▼
Helix Runtime presents grant request to user
    │
    ▼
User approves/denies/modifies each capability
    │
    ▼
Runtime creates restricted handles, passes to WASM module
    │
    ▼
Module operates within granted capabilities only
Any attempt to exceed → trap/abort

10. Specified Innovations
Each entry below is the design for an innovation candidate listed in TODO.md. The
decision recorded for each is the recommended option. Status says what the
repository implements today.

10.1 Capability Manifest Inference
Problem: authors hand-write the grants a guest needs, and over-granting is the usual
result. Decision: infer the manifest from the component's imports. A WASM component
lists the WIT interfaces it imports. Each Helix interface (dom, network, storage,
media) maps to one grant, and unknown imports are reported, not granted. The
inferred set is the minimal manifest, because wit-bindgen only imports interfaces a
guest calls.
Command: `helix manifest <component.wasm>` prints the grants.
Status: implemented (runtime `manifest` module, CLI `helix manifest`).

10.2 Capability-Diff on Update
Problem: an app update can silently request new capabilities. Decision: compare the
inferred grants of the old and new component and report added and removed grants. A
grant added by an update must be shown to the user before it applies. The runtime
computes the diff; the grant prompt is a UI concern outside this crate.
Command: `helix manifest <new.wasm> --diff <old.wasm>`. It exits with status 2 when a
grant is added, so a release pipeline can require review.
Status: implemented (runtime `manifest::diff`, CLI `--diff`). The user prompt is not built.

10.3 Migration Confidence Report
Problem: a migration report lists warnings but gives no single view of how far the
generated guest can be trusted. Decision: the report records four independent facts:
pattern fit, equivalence (S3), the count of warnings, and whether the generated crate
compiles for wasm32 (checked only when requested). It does not combine them into a
score, because a number would hide which check failed.
Status: implemented. The fields are the pattern, equivalence (S3), warning count, the
wasm32 compile result (`--check`), and the screenshot check. The screenshot check
rebuilds HTML from the S2 `DomOp` list (`migrate::reconstruct`), renders it and the
original at 800x600, and compares the PNGs with `screenshot_diff::compare`. Two limits
follow from the static renderer and are not hidden by the check. It paints rectangles
only, so text does not appear in either render. Style bodies are not carried into the
guest, so a lost stylesheet shows as a difference.

10.4 Signed Content-Addressed Bundles
Problem: an app must be verifiable offline, with no registry or network. Decision:
a bundle is a directory with a `bundle.json` that lists each file's relative path and
SHA-256, the app name and version, and an Ed25519 signature over the canonical
manifest bytes. The manifest's SHA-256 is the bundle's content id. Verification
recomputes every file hash and checks the signature against the public key in the
bundle. A key the verifier does not trust must be rejected by the caller, so the
bundle carries no trust decision of its own.
Commands: `helix bundle <dir> --key <seed-hex>` and `helix verify <dir> [--trust <pubkey-hex>]`.
Status: implemented (CLI `bundle` module).

10.5 Deterministic Host-Call Record and Replay
Problem: a bug seen in the field cannot be reproduced. Decision: record every
host-call result (dom, storage, network, media) as an ordered trace. Replay feeds the
recorded results back, so the same guest run is reproducible. Traces record results,
not timing, so replay does not depend on the clock.
Status: not implemented. It needs a recorder inside the host boundary, which touches
every `Guest` impl, so it is a separate change.

10.6 Hot-Reload Development Server
Problem: each code change restarts the app and loses DOM and storage state. Decision:
`helix dev` watches the component file and reloads it when it changes. Storage lives
in a per-app directory, so it survives the reload. The DOM is rebuilt by `run`, not
preserved, because the guest owns its DOM.
Status: not implemented. Durable per-app storage does not exist yet, and the storage
backend needs a design of its own.

10.7 Web/WASM Migration Playground
Problem: developers cannot see what a migration produces without running the CLI.
Decision: a static page with the JS source on the left and the generated guest on the
right. The migration runs in the browser, so the page needs no server. The migrate
crate's tree-sitter grammars must build for wasm32 first, which is unverified.
Status: not implemented. It is deferred until the tree-sitter wasm build is verified.
